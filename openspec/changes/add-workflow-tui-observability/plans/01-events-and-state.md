# Plan 1: Lifecycle Events and Observable Loss

## Scope and Acceptance

Loss is acceptable. The consumer must expose detected loss and must not claim completeness when it cannot establish it. Execution never waits for recovery, and the protocol has no replay, durable journal, or retry scheduler. This plan defines the observation contract before description and process integration.

Lifecycle completeness, available node state, trace availability, and captured diagnostic history are separate properties. A complete lifecycle stream does not imply complete traces or diagnostic history.

## Wire Contract

Use OTel LogRecord `EventName` for the five lifecycle names in the design, native timestamps and trace/span correlation, scalar attributes for routing, and a structured key/value body for event details. Do not JSON-encode the body into a message string. Use instrumentation scope `mf.workflow` to separate these records from plugin/application logs.

| Field | Encoding | Rule |
| --- | --- | --- |
| `mf.schema.version` | Signed integer | Initially 1; reject unsupported major versions |
| `mf.workflow.id` | String | `sha256:` followed by lowercase hex of the canonical compiled definition |
| `mf.run.id` | String | UUID v4 assigned at launch or generated by a standalone runner |
| `mf.event.sequence` | Signed integer | Starts at 1; increments before each lifecycle enqueue, including records subsequently dropped |
| `mf.node.id`, `mf.node.kind` | Strings | Present on node records; opaque values |
| `mf.outcome` | String | `succeeded`, `failed`, or `skipped` on terminal records |
| `mf.failure.phase` | String | `preparation`, `dependency`, `execution`, `publication`, or `output_selection` on failures |

Canonical identity input includes an identity-format version, the compiled definition, and execution order. Recursively sort object keys, preserve array order, and use one documented JSON encoding. Freeze bytes and expected digests in fixtures. The identity represents the embedded plan, not a binary digest or secrecy guarantee.

Event body fields are specific to the event:

- `mf.workflow.started`: `node_count` and `elapsed_ns = 0`.
- `mf.node.started`: `position` in the execution order and monotonic `elapsed_ns` from workflow start.
- `mf.node.finished`: `position`, `elapsed_ns`, available `duration_ns`, produced/skipped port-name arrays, and failure context when applicable. A pre-invocation failure has no execution duration.
- `mf.node.skipped`: `position`, `elapsed_ns`, causal source node/port pairs, and skipped output names.
- `mf.workflow.finished`: `final_sequence` equal to its own sequence, `elapsed_ns`, `visited_node_count`, optional `failure_node_id`, and workflow failure context. It contains no full per-node snapshot.

Nanosecond offsets and counts use nonnegative signed 64-bit integers. Optional values are absent rather than overloaded with zero. Unknown additive fields are ignored within a supported schema version; malformed required fields are rejected and visibly count against observation integrity.

`visited_node_count` counts the prefix of scheduled steps reached, including a step failing dependency resolution.
Preparation failure has a zero-length visited prefix. A preparation failure can identify a node anywhere in the order.
The identified failed node is Failed; other nodes are NotRun. For later failures, nodes beyond the visited prefix are
NotRun, excluding any explicitly identified failed node. Missing events inside the visited prefix leave node outcomes
unknown; aggregate workflow success cannot fill them in.

Only lifecycle events share the sequence. Plugin logs and trace spans do not consume it. There are at most `2 * node_count + 2` lifecycle records for this execution model. Emit the workflow finish last and reject further lifecycle emission through the completed observation scope. A failed serialization/enqueue still leaves a sequence gap; an exporter retransmission preserves the original sequence and content.

The embedded description exposes connected port names through edges, not the full effective port table. Receiver validation can check nonempty unique reported port names and skip causes against graph edges, but cannot prove that a reported list covers every dynamic output. Treat this unavailable metadata separately from lifecycle delivery loss. The runtime remains responsible for validating effective ports before event emission.

## Detecting Loss

Maintain received sequence membership bounded by the described graph's event maximum, per-node state, and explicit local-drop counters. Validate sequence bounds before allocating. A record counts as received for completeness only after decoding, session validation, and admission to the state reducer; acknowledgment by the HTTP handler alone is insufficient.

| Evidence | Display and behavior |
| --- | --- |
| Run active, no gap currently visible | Collecting; completeness has not been established |
| Higher sequence arrives before a lower one | Show a pending gap immediately; clear it if delayed records arrive |
| Valid final record, every sequence from 1 through final received and applied, no conflicts/local lifecycle drops | Complete lifecycle stream |
| Gap remains after bounded drain, or a local lifecycle record was discarded | Incomplete; show missing ranges/counts where known and the relevant reason |
| No final record by the drain deadline, including no records at all | Unverified tail; show that the final boundary is missing and the total missing count is unknown |
| Receiver, schema, or identity validation prevents interpreting the session | Show an observation error; retain known states and never claim completeness |

Known missing ranges and local drop counters can refer to the same records; do not sum them into a misleading total. A local display-history eviction has its own indicator and does not retroactively invalidate already applied lifecycle transitions. Trace sampling/export loss must never be described as a missing lifecycle record.

There is no heartbeat or independent reliable completion channel. If all future records are lost while a long node is running, immediate exact loss detection is impossible. Keep completeness unconfirmed throughout active execution; the process exit plus bounded drain exposes a missing terminal boundary. User-facing copy must distinguish proven gaps from inability to confirm completeness.

## State Reduction

| Current evidence | Incoming evidence | Result |
| --- | --- | --- |
| Pending | Node started | Running |
| Pending or Running | Node finished | Succeeded or Failed; a missing start does not prevent terminal state |
| Pending | Node skipped | Skipped, with causal ports |
| Terminal | Earlier start | Keep terminal; fill available timing metadata only |
| Any | Identical sequence and content | Ignore duplicate |
| Any | Same sequence with conflicting content or incompatible terminal outcomes | Record protocol conflict; expose uncertain state without silently selecting success |
| Unresolved | Valid final record proving node was not reached | NotRun |
| Unresolved | Process exits without sufficient node evidence | Unknown or Interrupted, with last known state retained |

Apply useful records immediately; missing global sequences do not stall all nodes. A gap invalidates confidence in unresolved current activity: show Running or Pending as last-known state until evidence resolves it. Do not overwrite successful prior nodes merely because the process later exits unsuccessfully.

## Implementation Order and Evidence

1. Define schemas and canonical-identity fixtures in `mf-telemetry`; deliver started, success, preparation failure, skip, and final-record examples.
2. Implement the per-run sequence producer and shared execution boundaries; verify a dropped enqueue consumes its sequence and exporters preserve IDs on resend.
3. Implement the pure reducer with bounded sequence tracking; verify every transition above independently of HTTP and terminal code.
4. Connect OTel emission and reception; verify start visibility while a node remains executing and finish delivery for short handled runs.
5. Exercise interior loss, prefix loss, final-record loss, an entirely lost stream, delayed gaps, malformed records, local queue overflow, and trace-only loss. Assert exact gaps only when evidence permits, and assert workflow outputs remain unchanged.

## Reference

[OTLP delivery semantics](https://opentelemetry.io/docs/specs/otlp/) allow duplicate records after retransmission. Application-level sequencing and completeness classification are the workflow contract defined here.
