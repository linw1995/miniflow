# Design

## Context

See [proposal.md](proposal.md) for motivation and scope. `Node::execute` currently returns a map of JSON values. `Flow::execute` and code generated by `CompiledWorkflow::generate_artifacts` independently gather every input and execute every node in deterministic topological order. Both reject absent referenced outputs.

Registrations expose static `PortSpec` arrays. Validation resolves ports from registrations before constructing instances, so a configuration-dependent number of branches cannot be represented. The structural planner deliberately runs without a plugin registry; plugin validation happens in the generated binary before installation.

`builtin.constant` and `builtin.identity` expose `Any` values. Existing type rules reject connecting `Any` outputs to concrete input types. Factories run during validation and execution and must remain free of business side effects.

## Goals / Non-Goals

**Goals:**

- Give both execution paths one explicit, deterministic skip protocol that third-party nodes can also use.
- Separate the dependencies that activate a node from the context references used to evaluate its conditions.
- Preserve ordinary plugin source implementations through additive trait methods and static-port fallback.
- Keep graph structure and generated execution order static while deriving node ports from validated configuration.
- Keep the core package free of network clients, database drivers, expression engines, and native service dependencies.

**Non-Goals:**

- Script expression parsing, compound boolean expression trees, field-to-field comparisons, implicit truthiness, loops, or concurrent execution.
- Resuming execution after mutually exclusive branches converge. A future merge node needs a separate input activation contract.
- Skipping factory construction or configuration validation for unselected branches.
- Inferring new static types from constant configuration or relaxing global `Any` assignability rules.

## Decisions

### 1. Organize basic nodes by dependency boundary

Create `crates/builtin-nodes/core` as package `mfn-core`, with `constant`, `identity`, and `if_else` modules. Register all three kinds when the crate is linked. Keep registration through inventory and explicit workflow dependencies; the CLI and compiler must not acquire production dependencies on the built-ins.

Move existing node behavior unchanged and remove the two old workspace crates. Update release support checks and packaged acceptance tests to select `mfn-core`. Existing published package versions, if any, remain historical artifacts; compilation does not rewrite user dependency declarations or locks automatically.

Separate packages per trivial node add release and dependency maintenance without isolating meaningful dependencies. Future service integrations remain separate packages. Simple condition evaluation is a private core module shared by routing code, without requiring users to assemble separate comparison nodes.

### 2. Use ordered branches with stable identifiers

The node configuration is:

```json
{
  "branches": [
    {
      "id": "preferred",
      "condition": {
        "source": { "output": "load_order.value", "path": "/amount" },
        "operator": "gte",
        "value": 1000
      }
    },
    {
      "id": "standard",
      "condition": {
        "source": { "output": "load_order.value", "path": "/amount" },
        "operator": "gte",
        "value": 100
      }
    }
  ]
}
```

`branches` is required and nonempty. Each branch requires one `condition`. IDs match `[A-Za-z_][A-Za-z0-9_-]*`, are unique and case-sensitive, and cannot be `else`. Unknown configuration, branch, and condition fields are rejected. IDs are stored unchanged; array order defines precedence.

For `N >= 1` branches, the instance exposes:

| Direction | Name | Declared type | Required | Meaning |
| --- | --- | --- | --- | --- |
| Output | `<id>` for each branch | `Boolean` | No | Activation value `true` when this branch wins |
| Output | `else` | `Boolean` | No | Activation value `true` when no condition is true |

There are exactly `N` configured predicates, no data input ports, and `N + 1` outputs. Incoming control edges govern activation; they do not supply condition operands. Outputs are derived from branches and cannot be configured separately. Every output is either produced or explicitly skipped on a successful invocation; `required: false` does not make omission an implicit skip.

The node evaluates predicates against the read-only context visible when it starts, in array order, and stops immediately after the first match. All-false predicates select `else`. The chosen output contains JSON `true` as an activation value; all other outputs are skipped. Runtime publication qualifies local branch names, such as `route.preferred` and `route.else`. Business data stays at its original qualified context ID. Branches do not copy a trigger payload or context into outputs.

This reuses the existing JSON output representation without introducing a fake business payload or a second signal value type. A control edge observes whether its source port was produced, not the truthiness of its value. The router's constant `true` identifies activation, while the separate skipped state identifies nonactivation. Ordinary data bindings can continue to fetch business data directly from its original producer.

#### Condition syntax and operators

Each predicate has a required `source` object with `output` and `path`, plus an `operator`. `output` is the exact
qualified ID `${node_id}.${output_name}`, such as `load_order.value`. `path` is a JSON Pointer within that output value:
`""` selects the root, `/customer/tier` selects nested data, and `/items/0/price` selects an array element. Decode `~0`
and `~1`; reject malformed pointer syntax during construction. Unknown source fields are rejected. Branches can
reference different prior outputs.

| Operator | Operand | Evaluation |
| --- | --- | --- |
| `eq`, `ne` | Required scalar `value` | Typed scalar equality or its negation |
| `gt`, `gte`, `lt`, `lte` | Required numeric `value` | Numeric ordering |
| `exists`, `not_exists` | `value` forbidden | Whether the path resolves |

Scalars are numbers, strings, booleans, and null. Equality compares strings exactly and case-sensitively, booleans and null by value, and numbers numerically. Different scalar types are unequal; no string-to-number or truthiness conversion occurs. Array or object operands are outside this first version: reject literals during construction and report an error when a reached comparison resolves to a container. Numeric ordering against a non-number is an execution error.

An unresolved path within a produced output returns false for `exists` and true for `not_exists`; all comparison
operators report a missing-field error. A skipped source port or node also counts as unavailable for existence checks; a
reached comparison against it is an error. A produced null value exists and can be tested with `eq` and a literal null.
Unexpectedly omitted outputs and unexecuted producers remain errors for every operator, including existence checks.
Missing business fields must not conceal scheduling or plugin defects.

Compare numbers without coercing all integers to `f64`, preserving distinct 64-bit integer values. Normalize the runtime JSON number's decimal representation into sign, digits, and exponent for comparison; numerically equal forms such as `1` and `1.0` compare equal. This operates on already parsed runtime values and does not promise arbitrary precision beyond the existing JSON parser. A small pure helper can implement this without an additional expression or decimal package.

Construction validates every predicate's syntax, operator, path escapes, and literal operand requirements, even in later
branches. Execution evaluates only reached predicates. A reached unavailable field or incompatible value stops execution
with consumer node, branch, qualified source output ID, path, and operator context; it is not treated as false. An unreachable
later branch can reference a skipped output or absent business field without failing that invocation, but its static
reference must still be valid.

When `ctx.outputs["load_order.value"]` contains `{"amount": 1500}`, the example selects `preferred` without evaluating `standard`. Amount `500` selects `standard`; amount `50` selects `else`. To route absent amounts explicitly, place a `not_exists` predicate referencing `load_order.value` and `/amount` before numeric comparisons.

### 3. Separate control edges and per-run context

Add an optional top-level `control_edges` array, defaulting to empty. Each entry contains `from_node`, `from_output`, and `to_node`; it has no target input binding. For example:

```json
{
  "control_edges": [
    { "from_node": "load_order", "from_output": "value", "to_node": "audit" },
    { "from_node": "audit", "from_output": "done", "to_node": "route" },
    { "from_node": "route", "from_output": "preferred", "to_node": "handle_preferred" }
  ]
}
```

Here `audit.done` activates `route`, while its predicate reads `load_order.value` from context. The dependency chain guarantees that the original output was resolved before routing. The trigger value never becomes the condition's data source. A node can have multiple incoming control edges, all of which participate in the same all-dependencies activation rule. Duplicate identical control edges are rejected.

Keep existing `edges` as data bindings with their current port/type rules. Plan a deterministic topological order over the union of data and control dependencies, deduplicating node pairs for graph indegrees. Validate cycles across both edge sets. Control edges require an existing source output and target node but no target data port or type assignment.

Create a fresh `ExecutionContext` for each invocation. Expose produced values through a flat `outputs` lookup keyed by `${node_id}.${output_name}`, using definition IDs rather than runtime indices. Retain node and port states alongside that lookup to distinguish skips, pending producers, and unexpected omissions. Publish all validated values and skip states atomically after a node resolves. Pending nodes have no readable value. Never expose partial outputs or retain values between invocations.

For example, a completed `load_order` returning local output `value` and a completed `load_customer` returning local output `value` produce these context entries:

```json
{
  "outputs": {
    "load_order.value": { "amount": 1500 },
    "load_customer.value": { "tier": "gold" }
  }
}
```

Nodes continue to register and return local names such as `value`. The runtime qualifies them once, using the executing node's definition ID. Explicit skip markers and implicit whole-node skip states resolve under the same qualified IDs. Declared source lookup must use the state-aware context API; lack of a key in the value map alone does not distinguish pending, skipped, and missing states.

After effective ports are resolved, build one index from each qualified ID to its `(definition node ID, local output
name, runtime node ID)` metadata. Treat references as opaque exact keys; never split them on the first or last dot. Dots
in existing node IDs or plugin output names remain valid when the resulting IDs are unique. Reject collisions before
execution: node `a.b` with output `c` and node `a` with output `b.c` both yield `a.b.c`. Report both producers and
require a rename; never choose a producer or overwrite a value.

The index includes every declared output, including potentially skipped ports. Data/control edges can keep their explicit source node and local port fields and resolve through this same metadata. Selected workflow outputs retain their user-specified result aliases. Qualification belongs to the context namespace and does not require plugins to know their workflow instance IDs or change local port declarations.

During an invocation the node gets an immutable view of context, containing all earlier resolved outcomes. It cannot mutate another node's outputs or publish its own outputs early. The sequential scheduler can lend a reference rather than cloning a context snapshot. After the node returns, the borrow ends and the scheduler records its outcome. Keep outputs until the run completes in this first version; liveness-based reclamation requires reference-aware analysis later.

The generated runner creates the same context and emits direct node calls plus publication steps in its fixed order. It does not interpret graph JSON. Data bindings, control gates, condition references, and selected workflow outputs read the same stored outcomes, avoiding separate histories with different availability rules.

#### Validate context references without adding execution dependencies

Add an instance method declaring qualified context output references, defaulting to an empty list for ordinary nodes.
If-else lists every configured source, including later branches. After resolving effective ports and building the unique
output-ID index, validate every reference by exact lookup and require its producer to be a strict ancestor through
explicit data/control dependencies. Unknown, self, descendant, and unordered references fail with consumer, branch, and
qualified output ID context.

References do not add edges or change scheduling. Users establish the necessary incoming path directly or transitively. An unrelated node sorting earlier by ID is not a sufficient ordering guarantee. This keeps scheduling visible in the graph rather than letting a condition edit silently change it. Runtime lookup still diagnoses pending or unexpectedly missing sources for lower-level callers and defective plugins.

A producer being an ancestor guarantees its outcome is resolved, not that every output is active. A reached existence predicate can inspect an explicitly skipped output, while ordinary comparisons report its unavailability. Context reads alone never activate or skip a node; only incoming dependencies gate execution. Plugins using context must declare their references, and the context view rejects undeclared reads rather than creating hidden dependencies.

### 4. Resolve effective ports from constructed instances

Add an optional object-safe method such as `Node::ports() -> Option<NodePorts>`, defaulting to `None`. `NodePorts` contains owned input and output descriptors, allowing branch names to be allocated from configuration. Convert existing static `PortSpec` values into the same owned representation when the instance supplies no override. Keep existing `NodeRegistration` fields and `PortSpec::new` unchanged.

An instance override replaces both registered port lists; it does not append to them. Reject empty names and duplicate names within each direction, and retain the existing type and required-input checks. Input and output namespaces are separate. Effective ports must depend only on configuration and must remain stable across validation and execution.

Refactor plugin validation to resolve registrations, construct each instance once per validation pass, resolve effective ports, and then check edges and workflow selections. Reuse those instances when constructing an in-memory flow rather than running factories again in the same pass. The generated binary's separate validation and execution invocations necessarily construct separate instances.

The CLI structural planner still knows only node IDs, edges, and selected outputs. It emits fixed port bindings and calls runtime helpers; the generated binary resolves effective ports using its selected plugins. No build-time registry protocol or hard-coded `builtin.if_else` recognition is introduced.

Changing registration arrays to mutable or leaked static strings would compromise ownership. An instance method accommodates configuration-dependent ports while leaving ordinary plugins unchanged.

### 5. Add explicit control results while preserving ordinary execution

Retain `Inputs`, `Outputs`, and `Node::execute`. Add a default context-aware execution method taking `Inputs` and `&ExecutionContext` and returning disjoint produced values and explicitly skipped output names. The default calls `execute` once and marks no ports skipped. Context-aware routers override the new method. Calling if-else's legacy context-free entry point returns a context-required error rather than synthesizing operands from `Inputs`.

The scheduler stores either a completed node result or a whole-node `Skipped` state. Whole-node skips are created when gathering inputs, without invoking either execution method. Source port lookup therefore distinguishes a value, an explicit skip, and an absent output. A skipped node resolves every declared output as skipped.

Shared helpers reject conflicting produced/skipped names and skip markers for undeclared or required output ports. An unexecuted node can propagate skips through all its ports, including normally required outputs. Unknown port bindings remain validation errors. Ordinary missing-output checks remain strict when an absent output is referenced; optional output metadata alone does not authorize a skip.

Flow construction through the compiler carries effective port information with the prepared node. Keep the existing low-level `FlowNode::new` construction path usable for ordinary nodes; add a constructor or builder for explicit resolved ports. In-memory controlled execution needs resolved output descriptors to validate explicit skip markers, and must diagnose missing descriptors rather than accepting unverifiable markers.

Representing skips with JSON `null`, absent map entries, or optional metadata would conflate control flow with valid data or plugin defects. Additive execution methods avoid requiring every existing plugin to wrap all of its output values in a new enum.

### 6. Use one activation rule in both execution paths

Resolve data bindings and incoming control edges in a canonical order by edge kind, target input when present, and source endpoint. Inspect all dependencies before deciding whether to execute:

1. If any referenced output is unexpectedly absent, return a contextual error, even if another input is skipped.
2. Otherwise, if any connected input is skipped, record the whole node as skipped.
3. Otherwise, assemble only the data-bound inputs and invoke context-aware execution once with a read-only context view.

Connected optional inputs and every incoming control edge participate in this rule. An unconnected optional input remains absent and does not block execution. A node without incoming dependencies executes normally if its context references are valid. A node gated by both mutually exclusive outputs is skipped; multiple incoming edges do not provide implicit merge behavior.

Canonical resolution and missing-output precedence prevent declaration order or an unrelated skip from hiding a plugin defect. Skip propagation follows edges; nodes with no dependency on an unselected branch still execute. Already executed independent nodes are not rolled back after a later error.

Factor input resolution, controlled invocation, and selected-output extraction into runtime helpers used by both `Flow::execute` and generated code. Generated code retains direct node calls and fixed order, storing node outcomes and guarding execution; it must not fall back to interpreting the embedded graph.

Factories may be invoked for skipped nodes. Configuration is checked for every node during validation, and factories remain free of business side effects. The guarantee is that skipped nodes' execution methods do not run.

### 7. Make branch-dependent workflow outputs explicitly optional

Extend output selections with `optional: bool`, defaulting to false and omitted on serialization when false:

```json
{
  "name": "preferred_result",
  "node": "route",
  "port": "preferred",
  "optional": true
}
```

| Source state | Required selection | Optional selection |
| --- | --- | --- |
| Value, including `null` | Include the key and value | Include the key and value |
| Explicitly skipped port or node | Return a skipped-output error | Omit the key |
| Unexpectedly absent output | Return a missing-output error | Return a missing-output error |

An optional selection still requires a valid node and port during validation. All selected outputs being optional and skipped produces `{}`. Output names remain unique; two branch selections cannot share a name to simulate a merge. `FlowOutputs` remains a JSON value map.

Keep schema `2026-09-26`: `control_edges` and `optional` are additive fields with unchanged defaults for existing definitions. New definitions using them require updated support packages; old readers reject the fields under their existing unknown-field policy. Serialize empty control edges and default-false flags away so old ordinary definitions remain portable. No support for schema `2026-09-24` is restored.

Unconditionally omitting skipped outputs would silently weaken existing output expectations. Keeping strict defaults makes branch-dependent omissions visible in the definition.

## Risks / Trade-offs

- [Condition syntax grows into an expression language] -> Start with one field-to-literal or existence predicate per branch; defer compound expressions, scripts, regular expressions, and field-to-field operands.
- [Missing and incompatible data select the wrong branch] -> Distinguish missing paths from null, reject reached invalid comparisons, and include branch, path, and operator context in errors.
- [Numeric coercion loses integer precision] -> Compare normalized runtime number representations and test adjacent large integers, signed/unsigned boundaries, decimals, and exponent forms.
- [Short-circuiting hides malformed configuration] -> Validate all predicate syntax during construction and short-circuit only data-dependent evaluation.
- [Context leaks across runs or exposes partial state] -> Allocate it per invocation, lend immutable access, and publish outcomes only at node completion.
- [Context storage grows with the workflow] -> Store output values once and retain them for the run; defer reclamation until context references are accounted for.
- [Dotted names create ambiguous output IDs] -> Resolve exact keys against a prevalidated index and reject collisions with both source pairs in the diagnostic.
- [Two execution paths diverge] -> Share helpers and run identical fixtures through in-memory execution and actual compiled binaries, comparing outputs, errors, and execution traces.
- [A skip hides a plugin defect] -> Preserve explicit missing states, validate skip markers, and inspect all input bindings before applying skip propagation.
- [Dynamic ports drift between invocations] -> Require configuration-only descriptors and exercise two instances of one kind with different branch sets in validation tests.
- [Package consolidation breaks declarations] -> Preserve kind names, document replacement of dependencies and locks, and test duplicate registration diagnostics when old and new providers coexist.
- [Optional outputs affect consumers] -> Keep required selections as the default and test omission separately from JSON `null`.

## Migration Plan

1. Consolidate the two existing built-ins into `mfn-core`, update workspace and fixture dependencies, and preserve their behavior with registry and execution tests.
2. Add instance-port resolution, context-reference declarations, and context-aware execution adapters, retaining ordinary plugin source implementations. Update plugin documentation alongside these APIs.
3. Add control edges, qualified output IDs, per-run context, shared activation/output helpers, both execution paths, and optional selections. Keep old definitions' defaults and update Rust struct callers with empty control edges and `optional: false`. Rename a node or output when distinct source pairs collide under the qualified-ID format.
4. Add `builtin.if_else` and examples where incoming control dependencies differ from the outputs read by predicates, including one and multiple conditions and optional branch results.
5. Update release package checks and packaged CLI acceptance. Release matching compiler/runtime support packages and `mfn-core` before distributing a CLI that requires them; publication is a separate maintainer action.
6. Users replace old built-in dependencies with `mfn-core` and regenerate adjacent Flow locks with an unlocked build, then return to `--locked`. Do not rewrite unrelated dependencies or the definition during compilation.

Rollback uses the previous CLI, matching support packages, old dependency declarations, and previous Flow locks. Existing standalone binaries remain usable. Conditional workflows require the new runtime and cannot be downgraded merely by deleting optional fields.
